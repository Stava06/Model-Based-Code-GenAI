The Model Is the System: Full-Stack Applications via MOSAIC - 
a Model-driven, OPM-based System with Agentic Iterative Code generation

INTRODUCTION
Model-Driven Engineering (MDE) has long promised to elevate models from documentation artifacts to first-class engineering assets [1]. Object-Process Methodology (OPM) [2], an ISO-standardized modeling language, provides a rigorous yet compact formalism that captures system structure, behavior, and purpose in a single, unified model expressed textually as Object-Process Language (OPL).
In practice, however, a persistent gap separates models from code. Once a development team transitions from modeling to implementation, the two artifacts diverge: the codebase grows, evolves, and accumulates design decisions that are never reflected back into the model. The model, originally the authoritative system description, becomes a historical artifact. This model-code drift is well documented [3] and represents a fundamental limitation of current MDE practice.
We propose to close this gap not by better synchronization tools, but by eliminating the manual translation step altogether. MOSAIC: a Model-driven, OPM-based System with Agentic Iterative Code generation, treats the OPM model as the sole persistent source of truth: a complete, runnable full-stack application is generated directly from an OPL specification, with no manual coding required. The model does not describe the system, the model is the system.
This idea has significant implications for MDE research and practice. If a formal conceptual model can reliably drive the generation of production-ready code, modeling transitions from a front-loaded activity performed before development begins to a continuously executable system definition that remains alive throughout the software lifecycle.
The contributions of this paper are: (1) a novel architecture in which an OPM model serves as the sole generative source for full-stack applications; (2) MOSAIC, an initial working implementation of this architecture based on Google's Agent Development Kit (ADK) [4]; and (3) a worked example demonstrating end-to-end generation from an OPL specification. The remainder of the paper is organized as follows: Section 2 reviews related work and identifies shortcomings of the state of the art. Section 3 presents the MOSAIC architecture. Section 4 demonstrates MOSAIC on a case study. Section 5 outlines future plans, and Section 6 concludes.

THE MOSAIC ARCHITECTURE
MOSAIC takes an OPL file - the textual representation of an OPM model as its sole input and produces a complete, downloadable full-stack project as its output. The system is built on Google's Agent Development Kit (ADK) and structured around three specialized agent roles that collaborate iteratively. The OPL specification is parsed into a logic map, then passed to the Supervisor, which orchestrates iterative generation and evaluation by the Generator and Critic agents. Figure 1 illustrates the overall pipeline.
 
The MOSAIC generation pipeline. 
- OPL Input and Logic Mapping
The user provides an OPL file specifying the target system. OPL is the natural-language subset of OPM: each sentence formally describes an object, process, state, or structural relation. Upon uploading, MOSAIC parses the OPL content and constructs a logic map - a structured internal representation that identifies all objects, processes, states, and relations. This logic map serves as the semantic backbone for all subsequent generation steps, ensuring that every generated component is traceable to a model element.
- The Supervisor Agent
The Supervisor is the orchestration layer. It receives the logic map, determines the sequence of generation steps, delegates tasks to the Generator and Critic agents, and decides when the output meets quality criteria sufficient for delivery. The Supervisor maintains the generation state across iterations, handles error recovery, and enforces architectural decisions (e.g., technology stack: React frontend, Flask backend, MongoDB data layer).
- The Generator Agent
The Generator receives a generation task from the Supervisor and produces the corresponding code artifacts as shown in Figure 2. For each task, the Generator is provided with the full logic map and the relevant architectural context, ensuring that generated files are semantically consistent with the OPM model. The Generator produces both frontend and backend components, including routing, data schemas, and deployment configuration files.
- The Critic Agent
The Critic evaluates the output of the Generator against three criteria: (1) graph coverage: the fraction of OPM objects, processes, states, and relations represented in the generated code; (2) syntax and executability: static checks for valid syntax, correct file structure, and resolvable dependencies; and (3) code quality: adherence to architectural conventions. The Critic returns a structured evaluation report, presented in Figure 2, that the Supervisor uses to decide whether to accept the output or request a refinement iteration.
